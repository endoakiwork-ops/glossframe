## 目標と利用者の操作

PC、ターミナル、ローカルへのクローンを使わず、説明サイトとCloudflare公式の「Deploy to Cloudflare」から自分用のアプリを作れるようにする。

1. GitHub Pages上の説明サイトから「自分用のGlossFrameを作る」を押す。
2. Cloudflareにログインし、GitHubとの連携を許可する。
3. 初期パスワードを入力する。
4. 既定の設定でデプロイを開始して待つ。
5. 発行されたHTTPS URLを開き、そのパスワードでログインする。

ログイン、アカウント作成・メール認証、権限許可、アカウント選択は利用者が行う。技術的な設定変更を不要にすることを目標とし、名前の衝突などを含む全状況で「次へ」だけで終わるとは約束しない。

## 採用する構成

- 説明HTMLとスクショは作成済みの [edoaki/glossframe-guide](https://github.com/edoaki/glossframe-guide) に置く。2026-10-23にREADMEの初回コミットと `main` のpushが完了済み。GitHub Pagesの共通サイトの構築・公開はAの実装担当が行い、Bでもそのサイトを使う。利用者はこのサイトをデプロイしない。
- 公式デプロイボタンの対象はアプリの公開リポジトリとする。利用者のGitHubにアプリがコピーされ、その人のCloudflareでビルド・デプロイされる構成を使う。
- 単語帳は利用者のD1、画像を保存する場合は利用者のKV、AI処理は利用者のWorkers AIを利用する。
- 説明サイトは認証情報を預からず、ログインとデプロイはCloudflare公式画面へ遷移して行う。独自のOAuth・デプロイ代行サーバーは初期版に含めない。

- [x] 必要なSecretを設定例で宣言し、デプロイ画面に用途が分かる説明を付ける。初期パスワードに共通の固定値を用意しない。

### 初期パスワードと所有者登録

初期版は「デプロイ前にパスワードを決める」方式とする。現状の `OWNER_SETUP_DISABLED` を単に解除して、最初にアクセスした人が所有者になれる状態にはしない。

- [x] 初期パスワードをCloudflareのWorker Secretとして受け取る。Git、説明サイト、ビルドログへ値を残さない。
- [x] 未登録状態では入力された初期パスワードを検証してから、所有者をD1へ登録する。D1には平文ではなくハッシュを保存する。
- [x] 初回認証にも試行回数制限を適用し、未設定のSecretや不正な入力では登録を拒否する。
- [x] 同時アクセスでも所有者が一度だけ作成されるようにし、所有者登録後は初期Secretを認証や上書きに使わない。
- [x] 初期登録済みの状態を維持し、再デプロイ・パスワード変更後に初期パスワードが復活しないようにする。
- [x] 通常のログイン・パスワード変更と、管理者向けの復旧操作を分ける。

デプロイ後にパスワードを新規設定する方式へ変える場合は、一度だけ使える初期設定キーなどで所有者を確認する設計を先に決める。

## 実装記録（2026-10-23）

- 配布設定は `wrangler.toml`。既存の個人用 `wrangler.jsonc` を優先し、そのまま保持する。
- `INITIAL_OWNER_PASSWORD` は空のSecret宣言と用途説明を用意。初回ログインだけで検証し、所有者は既存の主キー制約で一度だけ登録する。自由な所有者登録は明示的に有効化したlocalhost開発環境のみ。
- 復旧は別のSecret `OWNER_RECOVERY_TOKEN`。使用履歴のハッシュ、パスワード更新、全セッション削除をD1 batchで原子的に処理する。初期Secretでは復旧できない。
- 更新は `.github/workflows/mobile-update.yml` で公式版のコードをレビュー用ブランチへ取り込む。設定とDBはこの操作で変更しない。GitHub/Cloudflare実画面での確認は残る。
